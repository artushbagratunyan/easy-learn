# Easy Learn — план задач / Team Task Plan

> Команда: **COUnT, Артуш, Айк**. Все трое участвуют с первой волны. Имена GitHub-аккаунтов и точное распределение задач команда подтверждает перед созданием веток.

## Правила Git / Git workflow

### Ветки

- `main` — стабильная версия/релиз. Не вести обычную разработку напрямую.
- `dev` — общая интеграционная ветка. Все готовые задачи попадают сюда через Pull Request.
- Рабочая ветка создаётся от актуальной `dev` под конкретную задачу:
  - `feature/<short-name>` — новая функция;
  - `docs/<short-name>` — документация;
  - `fix/<short-name>` — исправление;
  - `design/<short-name>` — дизайн/UI.
- Примеры: `docs/project-architecture`, `feature/challenge-page`, `design/learning-dashboard`.

### Ежедневный порядок

```bash
git switch dev
git pull origin dev
git switch -c feature/<short-name>
# работа и небольшие коммиты
git push -u origin feature/<short-name>
```

Затем открыть PR **из своей ветки в `dev`**, описать изменения и проверить, что конфликтов нет. После ревью и согласования PR мержится в `dev`. Перед новой задачей обновить локальную `dev` и создать новую рабочую ветку.

### Коммиты и PR

- Один PR — одна логическая задача.
- Коммиты короткие и понятные: `docs: add project architecture`, `feat: add challenge preview`, `fix: handle empty answer`.
- Не коммитить секреты, `.env`, виртуальные окружения, `node_modules`, сборки и локальные базы.
- Не переписывать историю общей `dev` и `main` через force push.
- Изменения API, схемы данных и общих компонентов заранее сообщать в командном чате.
- Если задача не завершена, открыть Draft PR, чтобы показать прогресс и избежать параллельной работы над теми же файлами.

### Релиз

Когда версия готова: остановить новые изменения в релизной выборке, проверить `dev`, создать PR `dev → main`, провести финальный просмотр и только затем слить в `main`. После релизного merge отметить версию тегом, например `v0.1.0`. Для первого пустого репозитория сначала один раз создать начальную структуру и ветку `dev`; `main` оставить базовой стабильной веткой.

## Волны работ / Work waves

Работы идут волнами. Внутри каждой задачи владелец отвечает за реализацию и PR; остальные помогают ревью. Распределение ниже — стартовое предложение, команда может поменять владельцев до начала волны. Все трое участвуют с первой волны. В каждом разделе целевой объём — 10–20 задач; начать можно с 10 проверенных задач и расширять набор.

### Волна 0 — синхронизация и основа

**Цель:** договориться о продукте, репозитории, курсовом пути и минимальном каркасе.

- **COUnT:** владелец `ARCHITECTURE.md`; описать путь «выбор раздела → анимированный/видео мини-курс → 10–20 задач → мини-проект»; зафиксировать security требования.
- **Артуш:** владелец `TASK.md` и Git workflow; проверить настройки репозитория, подготовить `dev` и правила PR.
- **Айк:** продумать сценарии мини-курсов и анимаций; предложить задания, где ученик сам пишет/исправляет HTML/CSS/JS/Python, и дать ревью архитектуры.
- **Совместно:** подтвердить аудиторию, язык интерфейса, видео/анимации, необходимость аккаунта в MVP, 10 стартовых задач на трек и угрозы безопасности.

**Готово, когда:** документы просмотрены всеми тремя; стек и учебный путь зафиксированы; первая версия проекта и критерии MVP понятны; security gate принят командой; работа ведётся через ветки и PR.

### Волна 1 — технический скелет

**Цель:** запустить пустые frontend и backend отдельно и описать локальный запуск.

- **COUnT:** React shell, router и страницы Home/Tracks/Course/Challenge (заглушки допустимы); схема прохождения мини-курса.
- **Артуш:** Django/DRF project, health endpoint, конфигурация через env, базовый API route и первичный список серверных рисков.
- **Айк:** дизайн-система и адаптивные макеты раздела, главы мини-курса и задачи; сценарий анимации/видео; провести UX ревью каркаса.
- **Совместно:** README с командами запуска; договориться о формате API и структуре содержимого урока.

**Готово, когда:** frontend запускается; backend отвечает на health endpoint; основные страницы отражают путь «раздел → курс → задачи»; инструкции проверены минимум на чистой локальной настройке одним из других участников.

### Волна 2 — один вертикальный учебный сценарий

**Цель:** довести один учебный раздел от мини-курса до серии практических задач и проверки результата, затем повторить шаблон для остальных треков.

- **COUnT:** экран задачи, редактор и предпросмотр для HTML/CSS/JS; безопасный iframe sandbox; схема результата/ошибки.
- **Артуш:** модели/fixtures для track, course chapter, challenge; API выдачи глав и задач; сохранение попытки; серверная валидация и права доступа.
- **Айк:** сценарий одного мини-курса и анимаций; первые задачи на каждый трек и критерии проверки; подсказки и разборы.
- **Совместно:** пройти путь как новички; проверить, что анимация помогает понять код, а не заменяет практику; исправить непонятные инструкции.

**Готово, когда:** один путь «раздел → мини-курс → серия задач» работает end-to-end; для каждого трека есть набросок мини-курса и первых 10 задач; Python execution не запускается внутри Django-процесса.

### Волна 3 — прогресс и полнота MVP

**Цель:** связать главы мини-курса, проверку задач, прогресс и мини-проект; приблизить каждый трек к 10–20 качественным задачам.

- **COUnT:** состояния успеха/ошибки, подсказки, навигация по главам и задачам, прогресс, responsive polish.
- **Артуш:** API попыток/прогресса и persistence; проверки авторизации, валидации и безопасной обработки ошибок.
- **Айк:** довести курс и набор задач; проверить постепенный рост сложности, анимации объяснений и финальный мини-проект.
- **Совместно:** пройти весь MVP, собрать ошибки и приоритеты.

**Готово, когда:** пользователь может открыть раздел, пройти мини-курс, решить задания, получить разбор и увидеть прогресс; по каждому разделу есть от 10 до 20 готовых задач.

### Волна 4 — обязательный security-аудит

**Цель:** проверить приложение и исправить уязвимости до подготовки публичного релиза. Это обязательная волна, её нельзя пропускать ради срока.

- **COUnT:** threat model frontend, учебного редактора и preview; проверить XSS, DOM-вставки, iframe sandbox, `postMessage`, CSP и утечки в браузерных логах.
- **Артуш:** threat model backend/API; проверить SQL injection, CSRF, аутентификацию/авторизацию, object-level permissions, валидацию, rate limits, секреты, зависимости, production settings и безопасные логи.
- **Айк:** независимый security review задач/контента и пользовательских сценариев; проверить обход ограничений, небезопасный контент, загрузки (если есть) и понятность ошибок без раскрытия внутренних данных.
- **Совместно:** записать находки и severity, исправить и перепроверить все Critical/High; проверить запуск пользовательского кода. Если Python runner не изолирован, он остаётся выключенным/непубличным.

**Готово, когда:** заполнен release security checklist; нет открытых Critical/High находок; исправления повторно проверены; секреты не попали в Git; security review одобрен всеми тремя. Если аудит не завершён — релиз не готов.

### Волна 5 — релиз-кандидат

**Цель:** подготовить демонстрационную версию и релиз.

- **COUnT:** устранить UX-блокеры и собрать демонстрационный путь через курс и задания.
- **Артуш:** проверить конфигурацию, миграции, API и деплой-процедуру; подтвердить, что security gate пройден.
- **Айк:** финальная проверка контента, 10–20 задач в каждом разделе, инструкций, анимаций и подсказок.
- **Совместно:** открыть PR `dev → main`, повторно пройти release checklist и только затем слить и поставить тег `v0.1.0`.

## Definition of Done / Критерии готовности задачи

- Изменение соответствует своей задаче и не захватывает посторонние файлы.
- Инструкции и ошибки понятны начинающему.
- UI работает с клавиатурой и не ломается на узком экране (для UI задач).
- Для запуска кода есть изоляция; произвольный ученический код не исполняется в доверенном backend-процессе. Python runner остаётся закрытым, пока изоляция не проверена.
- PR указывает точки ввода/вывода и кратко описывает меры против XSS, injection, CSRF и нарушений доступа, если они затрагиваются.
- PR направлен в `dev`, содержит цель, изменения и ручные шаги проверки.
- Другой участник посмотрел PR; найденные замечания решены или отмечены.

## Release security checklist / Чеклист аудита релиза

- [ ] Threat model обновлён; перечислены доверенные границы и точки ввода.
- [ ] XSS проверен в страницах, редакторе, предпросмотре и отображении ответов.
- [ ] SQL injection исключён ORM/параметризацией; ручные SQL участки просмотрены.
- [ ] CSRF и cookie/session настройки проверены.
- [ ] Авторизация проверяется сервером для каждого приватного объекта и действия.
- [ ] Server-side validation, ограничения размера/частоты и безопасные ошибки проверены.
- [ ] iframe sandbox и сообщения между окнами проверены; ненужные разрешения отсутствуют.
- [ ] Python execution выключен или изолирован с лимитами и повторно проверен.
- [ ] Зависимости проверены; секретов и `.env` в Git нет.
- [ ] HTTPS, secure cookies, CSP и production settings проверены.
- [ ] Critical/High проблемы исправлены и перепроверены; результат аудита задокументирован.

## English summary

The team has three members: COUnT, Artush, and Aik. All three participate from Wave 0. Each language track starts with a short video/animated mini-course followed by 10–20 progressive coding challenges and a mini-project. Work is split into waves: product alignment, technical skeleton, one end-to-end learning path, progress/content completion, mandatory security audit, then release candidate. Create a task branch from `dev`, push it, and open a PR into `dev`; keep `main` stable and merge `dev` into `main` only for a reviewed release. Every public release is blocked until the documented security audit is complete and all critical/high findings are fixed and rechecked.
