# Easy Learn — последовательный план работ

## 1. Зафиксированные решения и текущая точка

- Дизайн **Build Coding Adventure** из Figma Make — визуальный и UX-ориентир. Код макета не задаёт архитектуру приложения.
- Стек: **React + Vite на обычном JavaScript, без TypeScript; Django + Django REST Framework; SQLite** на первом этапе. Next.js сейчас не планируется. Перед публичным запуском COUnT проверяет нагрузку записи и фиксирует решение: оставить SQLite или перейти на PostgreSQL.
- Направления: HTML Island, CSS Kingdom, JavaScript City, Python Universe. В макете показаны **29 миссий (7/7/7/8)**. Это целевой список для подготовки контента, а не утверждение, что задания уже написаны или безопасно исполняются. Старое требование «10–20 на каждый раздел» заменено этим ориентиром.
- Первый язык объяснений — русский. Расширение на английский и армянский планируется после проверки основного учебного пути; интерфейс готовить к локализации.
- Для внутреннего пилота допустим гостевой режим. Аккаунты, сохранение прогресса между устройствами и рейтинг включаются только после проектирования доступа и безопасности.
- В `dev` уже слит начальный каркас через PR №1: главная, страницы четырёх миров, Django health endpoint, README и `SECURITY.md`. **Редактор, реальные задания, проверка кода, аккаунты и прогресс ещё не готовы.**

Архитектурные решения описаны в [`ARCHITECTURE.md`](ARCHITECTURE.md), требования защиты и release gate — в [`SECURITY.md`](SECURITY.md).

## 2. Кто за что отвечает

### COUnT — руководство, GitHub, frontend и техническое качество

- Единственный владелец управления GitHub: структура веток, настройки репозитория и прав, Issues/Projects, правила PR, ревью и merge, CI, теги, релизы и синхронизация `dev` с `main`. Участники могут работать в своих ветках и предлагать PR; решение о слиянии и релизе принимает COUnT.
- Владелец React-интерфейса, интеграции с API, архитектурных решений по изоляции пользовательского кода.
- Владелец **технических тестов и аудитов всего приложения**, включая frontend и backend: стратегия проверок, автоматические unit/integration/API тесты, сборка, CI, нагрузочные проверки, анализ зависимостей, threat model, security-аудит и перепроверка исправлений. Разработчик проверяет свой код перед PR, но COUnT отвечает за технический gate.
- Ведёт журнал рисков и решений; при блокирующей проблеме меняет сроки или объём релиза открыто, не пропуская security gate.

### Артуш — Django/API и ручные проверки в реальной среде

- Реализует Django-модели, миграции, API каталога, попыток, прогресса и аккаунтов по согласованным контрактам. Передаёт COUnT описание новых точек ввода, прав доступа и способа проверки.
- Владелец **физических/ручных тестов**: запуск по README на отдельной машине, прохождение сценариев человеком, проверки в реальных браузерах и на доступных телефонах/планшетах, клавиатура, узкий экран, работа после обновления страницы, понятность ошибок. Фиксирует устройство, браузер, шаги, фактический результат, скриншот при необходимости и приоритет дефекта.
- Повторяет ручной сценарий после исправления. Не выдаёт сборку или автоматический тест за проверку устройства.

### Айк — обучение, контент и дизайн-система

- Владелец сценариев мини-курсов, объяснений, анимаций, учебных целей, заданий, подсказок, эталонных ответов и критериев проверки.
- Описывает визуальные компоненты и адаптивные состояния по Figma; передаёт COUnT готовые спецификации и проверяет соответствие готовых экранов смыслу макета.
- Проверяет, что каждое задание требует написать или исправить настоящий код, сложность растёт постепенно, а подсказки и ошибки понятны новичку. Не утверждает техническую безопасность кода или runner вместо COUnT.

### Общие правила

- Контракт API и формат задания согласуют COUnT, Артуш и Айк **до** параллельной реализации связанных частей.
- Для изменений аутентификации, исполнения кода, preview, загрузок и прав доступа нужен отдельный просмотр другим участником; технический аудит и решение о допуске остаются за COUnT.
- Разногласия по объёму, срокам и архитектуре записываются в Issue или в разделе «Открытые решения» ниже. Невыполненную задачу не помечать завершённой.

## 3. GitHub и порядок поставки

1. COUnT поддерживает `main` как стабильную релизную ветку, `dev` как интеграционную. Обычная разработка идёт в `feature/*`, `fix/*`, `design/*` или `docs/*` от актуальной `dev`. COUnT создаёт задачи и назначает владельцев.
2. Владелец делает небольшие коммиты, запускает относящиеся к работе локальные проверки, отправляет ветку и открывает PR **в `dev`**. В PR указывает цель, затронутые файлы/API, проверку, риски и ручные шаги для Артуша. Незавершённая работа — Draft PR.
3. COUnT проверяет diff, запускает технический gate/CI, организует ревью и единолично выполняет merge. Артуш прикладывает результат ручной проверки для пользовательских сценариев; Айк подтверждает содержание и UX для учебных экранов. Не использовать force push в общие `dev` и `main`.
4. Для документации плана COUnT может обновить `dev` напрямую, если задача явно требует этого; функциональные изменения идут через PR. Секреты, `.env`, локальные базы, виртуальные окружения, `node_modules`, сборки и экспорт `.make` не коммитить.
5. Публичный релиз: COUnT замораживает набор изменений, закрывает технический и security gate, получает отчёт Артуша по ручным тестам и подтверждение контента Айком, открывает PR `dev → main`, проводит финальный просмотр, сливает и ставит тег. При открытых Critical/High находках релиз не выпускается.

## 4. Волны и строгая последовательность

Волны идут в указанном порядке. Внутри волны задачи можно выполнять параллельно **после** согласования зависимостей. Следующая волна начинается, когда выполнен критерий выхода текущей; отдельные подготовительные материалы можно делать заранее без объявления волны завершённой.

### Волна 0 — согласовать первый учебный путь и рабочие правила

**Вход:** начальный каркас находится в `dev`.

1. **COUnT:** настроить GitHub-правила и список Issues по волнам; зафиксировать контракт задачи (`id`, трек, цель, стартовый код, подсказки, критерии, тип проверки) и минимальный API; определить, что входит во внутренний пилот и публичный релиз; обновить `ARCHITECTURE.md` при изменении решений.
2. **Айк:** составить реестр 29 миссий из макета с учебной целью и зависимостями; выбрать первые **три HTML-миссии** для сквозного сценария; написать для первой объяснение, стартовый код, ожидаемое поведение, 1–3 подсказки и критерии проверки.
3. **Артуш:** проверить запуск каркаса по README на своей машине; составить матрицу доступных устройств/браузеров и шаблон ручного отчёта; дать замечания к контракту API и модели данных.
4. **Все:** согласовать первую HTML-миссию и способ проверки без исполнения недоверенного кода в Django.

**Выход:** первые три миссии определены, первая полностью описана, формат задания/API согласован, GitHub Issues заведены, отчёт запуска Артуша записан. Владелец закрытия волны — COUnT.

### Волна 1 — достроить навигационный и визуальный каркас

1. **Айк:** передать спецификацию экранов World → мини-курс → Mission: состояния, тексты, размеры и поведение на узком экране; выбрать необходимые изображения/иконки из разрешённых материалов.
2. **COUnT:** реализовать эти маршруты и общий UI на React/JavaScript; связать переходы, состояния загрузки/ошибки и базовую доступность; добавить клиент API без доверенного рендеринга ученического HTML.
3. **Артуш:** уточнить backend-модель `Track`, `Lesson`, `Challenge` и миграции после согласования формата; подготовить read-only API каталога без выдачи скрытых ответов. Затем вручную проверить навигацию на реальных браузерах и узком экране.
4. **COUnT:** запустить сборку, Django checks, API/маршрутные проверки и анализ зависимостей; проверить изменения API и безопасности.

**Выход:** можно пройти из главной к описанию HTML-урока и миссии; данные приходят из API или явно помеченных fixtures; Артуш передал отчёт по реальному браузеру. Редактор ещё может быть заглушкой.

### Волна 2 — первая HTML-миссия от объяснения до результата

1. **Айк:** довести содержание первой миссии и два варианта ошибки/подсказки; описать, чему учится пользователь и что считается успехом.
2. **Артуш:** реализовать выдачу миссии и безопасный контракт результата; настроить валидацию входа и ограничение размера. Скрытые критерии не отправлять клиенту, если они дают возможность подделать результат.
3. **COUnT:** добавить редактор исходного текста и HTML/CSS preview в `iframe sandbox` по `SECURITY.md`; реализовать запуск/проверку только разрешённого типа задания и понятную обратную связь. Не выполнять ученический код в доверенном React или Django контексте.
4. **COUnT:** технически проверить XSS-границу, sandbox, CSP, API и ошибочные входы; добавить необходимые автоматические проверки.
5. **Артуш:** вручную пройти миссию на компьютере и доступном мобильном устройстве: успех, ошибка, подсказка, обновление страницы и клавиатурная навигация. **Айк** сверяет учебный смысл и тексты.

**Выход:** первая HTML-миссия работает от входа до результата и выдерживает технические и ручные проверки. До этого момента не копировать механизм проверки на остальные задания.

### Волна 3 — завершить HTML-пилот и сохранить прогресс

1. **Айк:** подготовить ещё две HTML-миссии, короткие главы мини-курса и мини-проект; показать рост сложности и критерии проверки.
2. **Артуш:** добавить попытки и прогресс в Django/SQLite, миграции и права на данные. Для пилота поддержать гостевой сценарий без притворной серверной авторизации; решение по аккаунтам согласовать до хранения персональных данных.
3. **COUnT:** связать главы, миссии, подсказки и прогресс в интерфейсе; реализовать технические тесты API, миграций, повторной отправки и доступа к чужим данным, если аккаунты уже появились.
4. **Артуш:** вручную пройти три миссии подряд и проверить возврат/обновление страницы; **Айк** исправляет учебные пробелы по результатам.

**Выход:** внутренний HTML-пилот из трёх миссий доступен от главной до прогресса. COUnT фиксирует, что переносить в другие миры, а что надо переделать.

### Волна 4 — остальные миры и полный учебный контент

1. **Айк:** подготовить и вычитать целевые **7 HTML, 7 CSS, 7 JavaScript и 8 Python миссий** с учебными целями, подсказками, тестовыми примерами и критериями. Для каждого мира — последовательность объяснений и итоговая практическая работа. Каждая миссия проходит контент-ревью до публикации.
2. **COUnT:** расширить интерфейс редактора и предпросмотра на CSS/JS, сохраняя изоляцию; технически проверить отдельные типы заданий и корректность критериев. Для Python сначала сделать threat model и выбрать изолированный способ исполнения; до его проверки публичное выполнение Python закрыто.
3. **Артуш:** расширить модели/API для всех миров, добавить необходимые миграции и сохранение прогресса; реализовать аккаунты только после согласования гостевого перехода, CSRF и прав доступа. Вручную проверять каждый завершённый мир на реальных браузерах.
4. **Все:** пройти учебный путь новичка. COUnT закрывает технические дефекты, Айк — проблемы объяснений, Артуш подтверждает исправления ручным повтором.

**Выход:** все 29 миссий готовы по содержанию и имеют поддерживаемый безопасный тип проверки. Если изолированный Python runner не готов, COUnT явно пересматривает дату/объём публичного релиза; нельзя объявлять Python-мир готовым или запускать код в Django ради срока.

### Волна 5 — техническая стабилизация и обязательный аудит

1. **COUnT:** провести технический аудит всего приложения: threat model, XSS и DOM-вставки, sandbox/`postMessage`/CSP, SQL-инъекции, CSRF, auth и object-level access, лимиты запросов, секреты, зависимости, ошибки и логи, настройки HTTPS/cookies. Отдельно проверить Python runner, если он есть.
2. **COUnT:** проверить нагрузку записи попыток/прогресса на SQLite, резервное копирование и восстановление; принять и записать решение о PostgreSQL до публичного запуска. Добавить CI-проверки сборки, Django, тестов и зависимостей.
3. **Артуш:** вручную проверить полный путь на фактических устройствах/браузерах, включая регистрацию (если есть), обрыв связи, перезагрузку, длинный код, узкий экран, клавиатуру и понятность ошибок. Зафиксировать воспроизводимые дефекты.
4. **Айк:** финально вычитать контент и интерфейсные тексты; проверить соответствие миссий целям обучения и дать замечания по доступности объяснений.
5. **COUnT:** устранить Critical/High, повторить техническую проверку исправлений и записать результат в `docs/security/` без секретов или деталей эксплуатации.

**Выход:** чеклист `SECURITY.md` закрыт, открытых Critical/High нет, технический аудит и ручной отчёт сохранены. Если gate не пройден, к релизу не переходить.

### Волна 6 — релиз-кандидат и публикация

1. **COUnT:** заморозить релизный набор, подготовить конфигурацию production, инструкции деплоя и отката, проверить миграции на копии данных и чистую установку.
2. **Артуш:** выполнить финальный ручной прогон релиз-кандидата на доступных реальных устройствах и браузерах; приложить результаты и повторно проверить исправленные дефекты.
3. **Айк:** утвердить итоговые тексты, порядок миссий и учебный сценарий демонстрации.
4. **COUnT:** повторить технические тесты и security gate на релизном коммите; открыть PR `dev → main`, проверить diff и результаты, слить его и поставить тег только после трёх подтверждений: технического COUnT, ручного Артуша, контентного Айка.

**Выход:** релиз опубликован, тег и версия записаны, известные ограничения и следующий список задач доступны команде.

## 5. Критерии готовности каждой задачи

- Есть конкретный результат и ссылка на Issue/PR; объём задачи не выходит за согласованный контракт.
- Владелец проверил свою реализацию. COUnT принял относящиеся к ней технические тесты и безопасность; для пользовательского сценария Артуш приложил ручной отчёт; для учебного материала Айк подтвердил содержание.
- Новые точки ввода/вывода, права доступа и выполнение кода описаны в PR. Никакие секреты или локальные данные не попали в Git.
- UI работает с клавиатуры, читаем на узком экране и показывает понятные ошибки. Непроверенные устройства или браузеры перечислены как ограничение.
- Для произвольного кода есть проверенная изоляция. Непроверенный Python runner остаётся выключенным; сообщения клиентского preview не считаются доказательством прохождения.
- Замечания ревью устранены либо открыто перенесены в Issue с приоритетом. COUnT принимает решение о merge в `dev`.

## 6. Открытые решения, которые надо закрыть вовремя

1. **До волны 1:** точный контракт урока/миссии/API и доступные для ручной проверки устройства Артуша.
2. **До волны 3:** хранить ли гостевой прогресс только локально или на сервере; как переносить его в аккаунт без потери/подделки данных.
3. **До Python в волне 4:** отдельный origin/browser runtime или изолированный серверный runner; модель угроз и лимиты. Решение фиксирует COUnT в `ARCHITECTURE.md` и `SECURITY.md`.
4. **До волны 5:** окончательный объём публичного релиза при готовности контента и runner. Цель — 29 качественных миссий, но число не может отменить требования безопасности.
5. **До волны 6:** результат проверки параллельных записей SQLite и решение по базе, резервным копиям и восстановлению.

## Кратко на английском / English summary

COUnT leads the project and owns GitHub administration, frontend integration, technical tests, CI, and security audits across the stack. Artush owns Django/API implementation and hands-on manual testing on actual browsers and devices. Hayk owns learning content, mission design, and visual specifications. The initial React/JavaScript, Django/DRF, and SQLite scaffold is already in `dev`. Work proceeds through product contracts, navigation, one secure HTML mission, a three-mission pilot, the remaining worlds and 29 target missions, mandatory technical/security audit, hands-on acceptance, and release. COUnT alone merges PRs and publishes releases; `main` stays stable. No public release proceeds with an incomplete security audit or unresolved Critical/High findings.
