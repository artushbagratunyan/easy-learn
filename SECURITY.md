# Безопасность Easy Learn

Этот документ задаёт начальные правила для сайта, где посетители будут писать HTML, CSS, JavaScript и Python. Он описывает требования к будущим функциям; наличие пункта здесь не означает, что он уже реализован. Сейчас каркас содержит страницы выбора миров и `GET /api/health/`. Редактор, запуск кода, аккаунты и сохранение прогресса ещё не включены.

## Сообщить об уязвимости

Не публикуйте рабочий эксплойт, чужой код или персональные данные в обычном GitHub Issue. Для приватного сообщения используйте **Report a vulnerability** в разделе **Security** репозитория, если GitHub Private Vulnerability Reporting включён. Пока этот канал не настроен, свяжитесь с владельцем репозитория напрямую согласованным с командой способом. Команда должна подтвердить получение, оценить влияние, устранить проблему и согласовать публикацию деталей после исправления. Сроки реакции и поддерживаемые версии будут указаны перед первым публичным релизом.

## Границы доверия и угрозы

Недоверенные данные: код ученика, названия и описания профиля, ответы API, параметры URL, сообщения между окнами, файлы и учебный контент из внешних источников. Доверенные компоненты: приложение React, Django API, база и учётные данные сервера. Даже учебный контент перед публикацией проходит ревью; сохранённый пользовательский код никогда не становится доверенной разметкой.

Приоритетные угрозы: сохранённый и отражённый XSS, выход кода из предпросмотра, доступ к чужому прогрессу, CSRF при сессионной аутентификации, инъекции, злоупотребление API и запуск произвольного Python на сервере.

## Обязательные правила реализации

### Пользовательский код и XSS

- Показывать исходный код как текст в редакторе и результатах. В React не вставлять его через `dangerouslySetInnerHTML`; не использовать `innerHTML` для ответов, имён, ошибок и подсказок. Не строить HTML, CSS или JavaScript в доверенном DOM из строк пользователя.
- HTML/CSS preview размещать в отдельном `iframe` с `sandbox` без `allow-same-origin`; не давать доступ к родительскому DOM, cookies и storage. Для JS preview понадобится `allow-scripts`, но сочетание `allow-scripts` с `allow-same-origin` на одном origin запрещено. Предпочтителен отдельный origin для preview. Запретить навигацию верхнего окна, формы, popups и загрузки, если они не нужны заданию.
- Для preview задать строгую CSP с явным решением по скриптам и сетевым обращениям; проверить фактическое применение CSP к `srcdoc`/preview-документу во всех поддерживаемых браузерах. Не считать CSP заменой sandbox и безопасного вывода.
- Если `postMessage` необходим, принимать только ожидаемые сообщения от текущего `iframe.contentWindow`, проверять схему, тип, размеры и идентификатор текущего запуска. У sandboxed документа без `allow-same-origin` origin может быть `null`, поэтому одной проверки `event.origin` недостаточно. При отдельном origin проверять его точное значение дополнительно. Никогда не принимать через сообщения команды на выполнение кода в основном приложении.
- Не исполнять код ученика через `eval`, `new Function`, обработчики событий в доверенном документе или React-компоненте. Сохранённый код, публичные решения и сообщения об ошибках проверять на XSS отдельно.

### API, доступ и данные

- Django ORM для обычных запросов; если нужен raw SQL, параметры передавать отдельно и проводить ревью. SQLite не устраняет риск SQL-инъекций.
- Для каждой операции с попыткой, прогрессом и профилем проверять пользователя и право на конкретный объект на сервере. Не принимать `user_id`, роль, награды или успешность задания как доказанный факт от клиента.
- При cookie/session auth использовать Django CSRF middleware и CSRF-токен для изменяющих запросов. CORS и SameSite не заменяют CSRF-проверку. Cookies в production — `Secure`, `HttpOnly`, осмысленный `SameSite`; сайт только через HTTPS.
- Ограничивать тип, длину, размер и частоту запросов на сервере; отдельно ограничить вход, отправку решений и запуск проверок. Возвращать безопасные ошибки без stack trace и секретов. Логи не должны содержать пароли, токены и полный приватный код без необходимости.
- Секреты передавать через переменные окружения/secret store; `.env`, базы, артефакты сборки и `node_modules` не коммитить. Зависимости фиксировать lockfile и проверять на известные уязвимости.

### Выполнение заданий

- Не выполнять присланный Python внутри Django, его worker-процесса или на том же хосте без отдельной доказанной изоляции. До готовности runner Python-задания должны работать без произвольного серверного исполнения.
- Для будущего runner: одноразовая среда без секретов и доступа к БД, запрет сети по умолчанию, лимиты CPU, памяти, времени, процессов, диска и вывода, очистка после задания и отдельное ревью модели изоляции. Web Worker улучшает отзывчивость интерфейса, но сам по себе не защищает сервер и не заменяет браузерную изоляцию.
- Проверка результата должна быть серверной или иной доверенной, когда результат влияет на прогресс/рейтинг. Клиентский preview даёт обратную связь ученику, но его сообщение нельзя считать доказательством успешного прохождения.

### Развёртывание и SQLite

- Текущая SQLite — выбор для начальной версии и локальной разработки. Файл БД хранить вне публичной раздачи, исключить из Git, ограничить права ОС и делать проверяемые резервные копии.
- Перед публичным запуском проверить параллельные записи попыток/прогресса и операционную модель: SQLite допускает одного писателя одновременно. При блокировках, очередях записи, нескольких экземплярах приложения или требованиях к высокой доступности перейти на PostgreSQL через проверенные миграции и резервное копирование.
- Перед production установить `DJANGO_DEBUG=0`, уникальный `DJANGO_SECRET_KEY`, явный `DJANGO_ALLOWED_HOSTS`, HTTPS, корректные trusted origins и заголовки безопасности. Запустить `python manage.py check --deploy`; проверять настройки на фактическом домене.

## Проверка перед каждым публичным релизом

1. Обновить список точек ввода и границ доверия; пересмотреть XSS в редакторе, preview, результатах, профилях и сообщениях.
2. Проверить sandbox, CSP, `postMessage` и отсутствие доступа к cookies/родительскому DOM на реальных браузерах.
3. Проверить CSRF, доступ к чужим объектам, SQL-запросы, ограничения размера/частоты и безопасные ошибки.
4. Проверить настройки production, секреты, зависимости, резервные копии и поведение SQLite под ожидаемой нагрузкой.
5. Проверить runner отдельно, если он появится. Записать результат аудита в `docs/security/` без секретов и деталей эксплуатации. Открытые Critical/High или незавершённый аудит блокируют релиз.
